- `crates/shard-core/src/lib.rs`

  - 新增优先级与多 type 归一化测试。
- `crates/shard-cli/src/parse.rs`
  - CLI 拒绝 `outline`、`flowchart`，错误文案为「终端不支持直接创建大纲或流程图。」；其余 type 标签按统一优先级归一化。
  - 新增受保护类型拒绝和 `document + note` 优先级测试。
- `src-tauri/src/lib.rs`、`src-tauri/src/search_sources.rs`
  - `Fragment` DTO 增加 `fileSha`。公开条目使用完整 Markdown 文件文本哈希，密匣条目使用完整加密文件文本哈希；普通读取、密匣读取和搜索结果三条构造链均已补齐。

  - 创建、正文更新和标签更新统一执行 type 单值及受保护规则；普通内容不能由正文标签变成大纲/流程图，已有大纲/流程图不会因保存丢失 type。
  - 创建到密匣、更新时转入密匣、结构操作移入密匣三条路径统一拒绝大纲/流程图；结构操作在 checkpoint 前拒绝，失败时文件位置、字节与 Git 状态不变。
  - 标签更新触发公开转密匣时改走携带新标签的内容搬迁路径，避免旧实现忽略新标签。
  - 新增完整文件基线、公开/密匣冲突、无基线保存、受保护 type 与三条密匣拒绝路径测试。

## 开工前 UI 基线

1. 已先执行 `pnpm install --frozen-lockfile --prefer-offline`，安装通过，复用 512 个包，lockfile 未变化。
2. 首次按 worktree 配置运行施工令列出的 10 个 spec，共发现 125 个用例：输出为 60 通过、65 失败。65 个确实运行在 1422 的用例因 `vendor/kiln` 未初始化、共享 CSS 无法加载而失败。
3. 随后发现两个大纲 spec 的自定义 fixture 把 `baseURL` 写死为 1420；上述 60 个“通过”实际误连用户主工作区，不能作为有效基线。发现后立即停止沿用该结果，并把 fixture 改为读取 worktree 配置。这是测试源码与 §4.5 的直接冲突，若不修复就无法满足“绝不连接 1420”。
4. `vendor/kiln` 远端无法直接取到仓库锁定的提交 `5e698208e5c54c92774ec74a362b309f405e0577`，因此从本机已有的主工作区 Kiln clone 获取同一提交并在当前 worktree 检出。之后，非写死端口的 65 个用例在 1422 通过。由于修正 fixture 本身属于必要改动，开工前无法再为那 60 个用例补做完全未改源码的 1422 基线；最终验收对全部 127 个用例统一使用 1422。

## 偏差

1. 施工令称前端 `Fragment` 位于 `src/lib/api.ts`，源码实际定义在 `src/types.ts`；按真实定义位置增加 `fileSha?: string`，API 文件只修改参数和 IPC 字段名。
2. 公开搜索结果的既有 `revision` 已是完整文件哈希，可同时作为 `fileSha`；密匣搜索结果的 `revision` 是解密 payload JSON 哈希，不能代表磁盘加密文件。密匣搜索加载时额外读取安全解析后的同一加密文件文本计算 `fileSha`，搜索 `revision` 语义保持不变。
3. `update_fragment_tags` 的公开转密匣路径原先调用“不带新标签”的结构搬迁 helper，会忽略本次标签更新。按源码事实最小改为内容搬迁 helper，沿用原正文并携带归一化后的新标签，没有扩大到其他结构操作。
4. `move_fragment_to_lockbox` 原先在读取 type 前先 checkpoint；为满足拒绝后 Git 状态不变，检查顺序改为先读取并拒绝受保护类型，再执行既有 checkpoint 和搬迁。
5. 两个大纲 UI spec 把端口写死为 1420，与施工令的隔离要求冲突；最小修改为读取 Playwright `baseURL`，并保留默认配置不变。
6. 当前分支缺少 `docs/design/frontend.md`，因此只读参考了主工作区同名文件确认 pointer-first 产品选择；没有修改当前 worktree 之外的文件。Kiln 规范则使用当前 worktree 检出的锁定提交完整阅读。
