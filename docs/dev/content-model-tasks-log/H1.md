# H1：受管 JSON 区域与后端读写命令

## 改动文件与要点

- `crates/shard-core/src/graph_region.rs`
  - 新增大纲 `shardmap`、流程图 `shardflow` 两种受管区域的查找、渲染与替换。
  - 区分无区域、多个同名区域、两种区域并存、围栏未闭合四类中文错误；开围栏允许行尾空白，闭围栏必须位于第 0 列且不能带行尾空白。
  - Rust 与 TypeScript 对 LF、CRLF、开围栏尾空白和 JSON 尾换行采用一致规则；替换时逐字节保留区域前后正文。
  - 新增 10 项单元测试。
- `crates/shard-core/src/lib.rs`
  - 注册 `graph_region` 模块。
  - 新增可指定 `id` 与创建时间的公开碎片创建变体，原入口继续自行生成 `id` 后委托该变体；用于在图 JSON 落盘前先确定碎片 `id`，并拒绝覆盖同名目标。
- `src-tauri/src/canvas_commands.rs`
  - 将既有 `canonical`、`validate_file` 最小提升为 `pub(crate)`，供 H1 流程图片段复用同一格式与校验合同。
- `src-tauri/src/lib.rs`
  - 新增 `create_graph_fragment`、`read_graph_fragment`、`write_graph_fragment` 三个异步 Tauri 命令并注册；文件系统与 JSON 重操作均在后台线程执行，创建和写入在取得 vault 后立即持有写门，内容写入只落盘、不内嵌 Git 提交。
  - 创建大纲时由后端覆盖 `id`、类型、schema、应用版本、revision 与时间戳后校验；创建流程图支持空 graph，生成标题为「未命名流程图」的空 `shard.flow`。
  - 创建标签强制只保留请求的 `outline` 或 `flowchart` type，并拒绝密匣标签。
  - 增加按 vault 隔离、最多保留 256 条的进程内 operation receipt；同一 `operation_id` 重试返回原条目，不同 kind 直接拒绝。
  - 读取按磁盘 frontmatter type 选择对应围栏与结构校验，不为缺失或损坏区域生成空图。
  - 写入先校验完整文件 `fileSha`，以磁盘当前 revision 为基线递增并更新 `updatedAt`；只替换受管区域，通过 `apply_frontmatter` 只更新 `updated_at`，原子写入，区域外正文及未涉及 frontmatter 原样保留。
  - 普通 `update_fragment` 遇到有效、多个、混合或未闭合的受管区域统一拒绝，旧式纯缩进列表大纲仍可保存；标签、置顶、关联等 frontmatter-only 路径未改。
  - 新增 8 项后端临时 vault 测试，覆盖 §5.3 的创建、读取、幂等、保真写入、STALE_BASE、400 节点上限、文本保存保护和密匣拒绝。
- `src/lib/graph-region.ts`、`src/lib/graph-region.test.ts`
  - 新增与 Rust 规则一致的 `findGraphRegion`、`renderGraphRegion`、`replaceGraphRegion`，新增 11 项单元测试。
- `src/lib/api.ts`
  - 新增 `createGraphFragment`、`readGraphFragment`、`writeGraphFragment` 类型化封装；返回结果统一 hydrate `Fragment.kind`。
- `docs/dev/content-model-tasks-log/H1.md`
  - 记录本批实现、验收结果、偏差与遗留问题。

本批未修改任何 UI 组件、样式或依赖，也未运行 Playwright。既有未跟踪文件 `playwright.worktree.config.ts` 保持不变。

## 偏差

1. 施工令允许“需要时”在 shard-core 增加可指定 id 的最小变体；源码中的 `create_public_fragment_in_vault` 会在函数内部生成 id，无法先把同一 id 写入 graph，因此新增 `create_public_fragment_with_id_in_vault`，原入口委托它；正常创建的路径、frontmatter 与标签规则保持不变，指定 id 变体额外拒绝覆盖已存在目标。
2. 既有流程图 `CanvasFile`、`validate_file`、`canonical` 位于 `src-tauri/src/canvas_commands.rs`，其中后两者原为模块私有；按源码事实仅提升到 crate 内可见，未复制流程图格式或校验逻辑。
3. 前端 `CanvasFile` 类型实际定义在 `src/features/canvas/model.ts`，不在 `src/lib/api.ts`；API 封装直接导入既有类型，没有新建重复合同。
4. operation receipt 的内部 key 使用“vault 路径 + operation_id”，而不是跨所有 vault 共用单一 operation_id。这样仍满足同一 vault 内的重试幂等，同时避免用户切换 vault 后偶然复用 operation_id 时返回另一座 vault 的碎片。
5. `write_graph_fragment` 未复用 `write_fragment_update`：该函数会 trim 正文尾部并重建正文分隔，无法满足“区域外正文逐字节保留”。实现改为 `apply_frontmatter` 后拼回原 `parsed.body`，再调用既有 `write_text_atomically`；写入仍为原子操作。
6. §5.4 列出两项允许的既有前端单测失败，本次实际只出现 `roundtrip.test.ts`；`quick-open-perf.test.ts` 在同一轮全套测试中通过，因此没有单独复跑或把它记为失败。
