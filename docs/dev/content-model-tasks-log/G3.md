## 偏差及原因

1. 未实现搜索面板中 `#标签` 候选。当前打开模式的搜索结果是带真实对象与既有打开分派的强类型目录项，把标签主题页混入会扩大搜索合同和路由分派范围；§15.1 明确允许现有结构不便时只实现卡片和筛选状态条两个入口，因此本批不扩展搜索架构。
2. 当前 `FragmentCard` 的标签只展示，不传 `removable` / `onRemove`，仓库没有可从真实卡片触发的「删除标签」入口，无法按 §15.3 做端到端删除回归。`TagBadge` 仍按施工令保留了打开与删除的独立同级命中区，并在删除动作阻止冒泡；没有为测试虚构生产入口。
3. 既有 `FragmentBacklinksPanel` 面向单个目标并在空数据时渲染空状态，不能直接表达主题页的多目标聚合和「为空不显示」。本批沿用同一 `Fragment.related` / wikilink 数据来源，以局部聚合列表做最小适配，没有改动资料库检查器的既有面板。
4. 工作台当前冷启动统一进入默认碎片页，已持久化的其它 route 也不会在启动时恢复。G3 沿用这项源码事实：主题路由通过既有效果写入，视图选择按标签写入 localStorage；刷新验收采用「刷新后重新进入同一标签」，没有为 G3 单独改变全局启动语义。
5. 初次完整单测运行时，`quick-open-perf.test.ts` 曾在并发负载下出现一次 p95 超限；单文件隔离复跑 2/2 通过，最终再次按原命令完整运行时该性能用例 2/2 通过，仅剩施工令已注明的 golden 夹具失败。没有修改无关性能门槛或 quick-open 实现。
6. `docs/dev/content-model-tasks-log/G3.md` 受仓库现有 `docs/dev/*` 忽略规则影响，不出现在普通 `git status` 中；仍按施工令创建并直接读取核对，没有 stage、commit 或修改 `.gitignore`。
