# Shard 仅碎片产品迁移方案

状态：**设计完成 / 代码未实施**。日期：2026-09-15。

已依据一轮 Grok 审计修订，具体意见与处理见 [审计记录](fragment-only-grok-audit.md)。总实施顺序以本文件 0–5 为准，存储方案 A 为前置数据基础，B–D 是本文件阶段 4 的内部工作，最后统一进入阶段 5 验收。

本文件定义从现有多模块 Shard 收敛为仅碎片产品的迁移边界、数据留存、实施顺序、验收和回滚。产品定义见 [fragment-only-design.md](./fragment-only-design.md)，连接及同步协议见 [fragment-storage-sync.md](./fragment-storage-sync.md)。后续实施应同时满足三份文档，不能把本文件中的实施计划当成已经存在的能力。

本次只交付设计文档，没有修改源码、测试、依赖、配置或真实 Vault，没有执行数据转换、导出、联网同步、安装、启动 Shard 或数据服务、提交或发布。现有源码工作区改动保持原样；后续实施须重新核对当时的工作区与数据状态。

## 1. 迁移目标与不变量

Shard 的日常产品只围绕碎片：记录、编辑、时间线、搜索、标签、置顶、碎片关联、附件和回收站。**用户已确认保留私密碎片，取消独立密匣工作台**；私密是碎片的受保护状态，不是退场内容类型。本地离线能力独立成立；Git、飞书、夸克可以同时配置，并分别调整或暂停。首版每个碎片库至多一个主要双向通道，其余连接作为备份；全关即纯离线。Hermes/OpenClaw 是外部记录入口，不成为新的内容类型或本地工作区。

以下边界贯穿整个迁移：

- **产品移除不等于数据删除。** 删除菜单、路由、编辑器和模块代码，不得连带删除用户文件、Git 历史、回收站、密钥元数据或共享附件。
- **默认不做内容转换。** 旧资料仍在原位置留存，只有用户选择的旧内容才转成新的碎片；原件保留。不得自动把每个表格行、导图节点或画布节点生成碎片。
- **普通 Markdown 表格属于正文能力。** 保留解析、显示、编辑、复制粘贴、序列化和已有内容；移除的是具有独立字段、记录、视图和导入工作区的多维表格产品。
- **共享包不随产品模块退场。** `packages/markdown` 的导出、普通表格、任务列表、解析 Worker 和样式继续服务 Shard 及其他消费者；不能借本次迁移变更其他项目或发布不兼容包。
- **隐私边界不因产品精简而改变。** 保留私密碎片既有的加密、解锁、自动锁定及安全读写能力，原件按密文保留；不能利用当前已解锁会话自动导入公开碎片、交给 Agent 或同步成飞书明文记录。
- **内容与连接状态分离。** 本地已保存、Git 已提交、远端已接收、备份已验证是不同事实；移除模块不得将所有状态压成一个成功标志。

## 2. 当前实现与共享边界

本节依据当前工作区的只读检查，描述现状；文件行号可能随后续实施变化，以符号及路径为定位依据。

| 现有边界 | 源码证据 | 对迁移的影响 |
| --- | --- | --- |
| 主壳层同时编排碎片、资料库、密匣、图类视图 | `src/workspace/workbench-shell.tsx`、`route.ts`；`fragments-workspace.tsx` 仍接收 `MindMapPanel` | 不能只隐藏侧栏；要移除退场模块路由及依赖，私密碎片的解锁、保存门禁和自动锁定迁入统一碎片链路 |
| 碎片与资料库 Markdown 共用 `Fragment` | `src/types.ts` 的 `Fragment`；`src/lib/content-kind.ts` 根据 `note` 标签判断类型；`src-tauri/src/lib.rs` 的 `list_fragments_in_vault` | 列表同时扫描 `fragments`、`.trash/fragments`、`notes` 和解锁后的密匣；仅碎片索引需明确收录范围，不能把所有旧 Markdown 自动纳入 |
| 读取链路可能触发旧迁移 | `workbench-shell.tsx` 的 `prepareLibraryTree` 调用 `migrateLegacyNotes`；Rust `migrate_legacy_notes` 还处理旧 archive 与导图 | 新版首次启动和迁移预检不得沿用会搬文件的旧初始化路径；先完成无写入的盘点 |
| Git 托管范围覆盖多模块 | Rust `MANAGED_VAULT_ROOTS` 包含 `fragments`、`notes`、`.trash`、`assets`、`maps`、`lockbox`、`.shard` | 必须将“新版索引哪些内容”与“旧仓库已跟踪哪些路径”分开；不能通过删目录或 `git rm` 收窄产品 |
| 附件不是资料库私有资源 | `save_fragment_image` 写 `assets/<hash前两位>/<hash>.<扩展名>`；`fragment-images.ts` 兼容路径和 `shard-attachment:` 引用 | 碎片、旧文档和旧图类数据可能共用图片；移除资料库资产浏览器不构成删除图片的依据 |
| 编辑器保留普通 Markdown 表格，但文件拖放引导仍指向多维表格 | `src/editor/extensions/table-widget.ts`、`src/editor/table-widget-host.tsx`、`src/components/shard/editor-table.tsx`、`src/lib/use-table-document-drop.ts` | 保留正文表格链路；移除“到资料库的多维表格菜单导入”的失效引导，不借此新增完整表格导入产品 |
| 旧结构化文档有额外恢复资料 | `src-tauri/src/canvas_commands.rs`、`canvas_commands/split.rs`、`table/storage.rs`；Rust `mind_map_last_good_rel_path` | 原始 JSON 之外还需保留现有恢复副本、冲突副本、拆分记录和隐藏元数据，不能只导出当前屏幕显示内容 |

迁移盘点必须从文件清单出发，不能直接使用现有 `list_fragments_in_vault` 的成功解析结果计数。该函数会过滤读取失败的条目；损坏 frontmatter、未知 schema 和无法读取的文件必须进入盘点报告，而不是被当成不存在。

新增同步元数据时，以 [存储方案第 3.2 节](fragment-storage-sync.md#32-当前正文日志与索引的关系) 的路径/托管表为实施门禁：库内只增加可移植恢复信息，设备队列、运行锁、索引与映射缓存位于 Vault 外；核对实际 Git 跟踪和备份清单，而非只看忽略规则。密文和加密恢复元数据按授权成套保留，不误删 `lockbox.json`。这是后续数据基础阶段的显式格式升级，不能在本节只读盘点或首次壳层切换中偷偷写入。

## 4. 旧数据无损留存与导出

### 4.1 默认留存策略

首次运行新版只改变产品可见范围，不重写旧文件，不缩窄现有仓库的 Git 跟踪清单，不执行旧自动迁移。原有文件夹和 ID 是恢复依据，不能仅为目录整齐而集中搬到新的 archive 目录。

设置提供低频“旧数据”入口：查看盘点结果、导出原始资料、选择性导入公开内容、查看恢复说明。它不提供旧模块的新建和日常编辑功能。未出现旧数据时无需制造固定提醒。

同一个 Vault 被旧版、其他设备或 Git pull 写入旧文档后，新版继续原样留存并报告新增的旧资料；不得重新启用旧模块，也不得自动把这些文件当成新碎片或删除事件。

### 4.2 盘点与原始资料包

后续迁移工具按以下顺序工作，所有扫描、校验、打包和大批量转换在后台运行：

1. 确认当前 Vault 身份与真实目录、当前分支和未保存状态。只读盘点不调用 `ensure_vault_layout`、`migrateLegacyNotes` 或任何可能写入的初始化接口。
2. 枚举旧模块目录、现有 `.trash`、共享 `assets`、恢复与冲突资料，以及未知文件；不跟随逃出 Vault 的符号链接。对不可读文件保留路径和错误，不能用成功解析数量替代完整数量。
3. 形成带版本的清单：相对路径、类型识别、字节大小、内容哈希、可安全识别的原 ID、源位置与读取错误。密匣仅记录密文文件事实，不为盘点获取正文或解锁。
4. 导出到用户选择的新目录或资料包，保留相对路径和原始字节。完整原始资料包包含已有共享附件及恢复元数据；针对单一旧模块的导出如不能证明附件引用完整，应保留全量附件副本，不做垃圾回收。
5. 校验导出后每个文件的哈希、文件数和大小，并验证没有源内容在复制期间变化。源文件变化时使该次结果成为“未完成/需重试”，不能把不一致包标为完整；已写出的临时包不覆盖先前成功包。
6. 给出恢复说明和校验结果。任何不可读、缺失或变化文件都阻止“无损导出完成”的结论。取消或中断不改变源数据；重复执行不会重复导入或覆盖原件。

Git 历史是独立的恢复材料：仅复制受托管内容文件不能声称已经保存 Git 历史。需要完整回退环境时，在一致状态下另行保存本地 Vault 快照及本地 Git 元数据；对外分享的资料包不默认附带 `.git/config`、凭据或其他连接私密配置。

### 4.3 可读导出与选择性转入碎片

| 旧内容 | 可选的便携副本 | 必须保留的原件和限制 |
| --- | --- | --- |
| Markdown 文档 | Markdown；用户选择后按一篇文档生成一条碎片 | 保留原文件、原 frontmatter、正文、创建信息及路径；不自动拆段。移除结构性 `note` 标记的处理只作用于新副本，其他标签保留 |
| 思维导图 | Markdown 大纲或文本 | 大纲不能完整表达布局和所有节点属性，`.shardmap.json` 才是无损原件 |
| 多维表格 | CSV/XLSX，必要时附字段和视图说明 | 不保证便携格式完整承载类型、视图、筛选、分组、排序、隐藏列等语义；原 `.shardtable.json` 必须保留 |
| 画布/流程图 | 文本摘要或视觉预览 | 不自动把节点文本作为完整导出；原 JSON 保留坐标、连线、引用和嵌入内容 |
| CSV、附件及其他文件 | 按原格式复制 | 不重新编码或因新版不支持打开而跳过；路径引用需可回溯 |

导入碎片应带有可重复执行的来源映射：源路径、源 ID、源内容哈希和新碎片 ID。原 ID 唯一且未使用时可以保留；与已有碎片冲突时不得覆盖，而应生成新 ID、保留来源映射并报告冲突。原件不删除；正文内旧引用不静默改写。选中的来源同时导入后，可以依据完整映射调整新副本内部关系，无法解析的目标保留为未解析引用。

新版正常读取不依赖完成这些可选转换。不能以“用户还没有导出”为由强制继续维护整套资料库工作区，也不能以“用户未选择转换”为由删除旧数据。

### 4.4 私密碎片与旧密匣数据专项约束

私密碎片继续日常可用：新建、编辑、显式选择普通/私密目的地、解锁和自动锁定，均复用现有安全语义。主导航的“私密碎片”是受门控的碎片筛选，不能退化为仅有设置中的一次性旧数据导出入口；独立 `lockbox` 工作台路由不再存在。私密内容不进入公开搜索、关联候选、公开导出或 Agent 上下文；锁定后需要撤下受保护的视图、缓存及搜索结果。私密旧文档若带有资料库身份，则按旧格式保留和选择性迁移，不因其已解锁而混入私密碎片流。

保留现有不支持私密图片附件的限制，不因复用普通编辑器而开放向公开 assets 写入的旁路；未支持的图片或文件附件在私密模式下不可追加。带附件内容转私密必须保留原件并拒绝未支持转换。普通转私密的未发送队列、传输中结果和旧 Git 明文历史按同步文档处理，不能仅移动界面归属后继续自动外发。

现有图片拒绝逻辑覆盖有限，复用编辑器时须按同步文档补齐行内、引用式、HTML 图片及本地附件引用的统一校验。保留已配置写入公钥时的锁定投递能力，读取和编辑仍需解锁；当前离开自动上锁依赖 `route.space === "lockbox"`，必须改为明确的私密阅读范围条件，不能删除旧路由后让所有私密视图立即上锁或失去上锁。

普通目的地在私密视图下须经过本次保存确认；私密来源派生产物继承隐私，首版不向 AI/Agent 发送私密来源。转私密预览按目标列出旧明文修订和备份，不能因为投影撤下、暂停连接或新建目标就宣称旧副本不可读。

密匣原始资料包必须同时保留 `lockbox/` 内实际存在的密文与 `.shard/lockbox.json`，包括密码/恢复密钥所需的加密主密钥、盐、nonce 和写入密钥元数据。只保留密文正文或只保留清单文件，都不能声称可恢复。

自动迁移和默认导出只复制密文；不新设密码、不重置密码、不生成替代密钥，不把解锁状态当成公开授权。明确选择“解密导出”时才进入独立流程，由用户完成解锁并选择本地目标与具体内容。它不自动把明文转成公开碎片，也不自动加入飞书、Git 新目标或夸克目标。

取消独立工作台之前，须在复用后的碎片流中验证私密创建、读取、编辑、锁定、错误恢复和显式转入私密的安全落盘；原子写入、失败不丢原件、写入门与既有密码恢复方式不能回退。还须验证当前读取/导出实现或保存的旧版/专用离线恢复工具能以原密码和已有恢复凭据读取测试密文包。只留下密文而没有可用工具不算保留完成；不开放独立密匣工作台不影响私密碎片的日常使用。

## 5. 分阶段实施顺序

以下全部是待实施工作。每个阶段都要求独立差异与相应验证，阶段完成不代表获得提交、push 或发布授权。

| 阶段 | 实施范围 | 进入下一阶段的证据 |
| --- | --- | --- |
| 0. 基线和迁移准备 | 核对真实工作区；记录既有修改；用测试 Vault 建立旧格式、附件、回收站、密文和异常文件夹具；确认旧版恢复路径 | 只读盘点能覆盖未知/损坏文件；原始资料包校验和恢复演练完成；真实用户数据未被转换 |
| 1. 仅碎片产品壳层 | 收敛路由、菜单、搜索类型、创建入口和对话框；私密碎片接入同一碎片流并保留解锁门；去掉 `prepareLibraryTree` 引发的自动迁移；首次启动不触碰旧目录 | 本地离线可创建/编辑/查找公开与已解锁私密碎片；无旧独立工作台入口；旧路由安全落回对应碎片状态；旧数据字节未变 |

| 5. 发布候选验收 | 用全新 Vault、混合旧 Vault、无 Git Vault、断网和多连接组合完成桌面验收；形成迁移/恢复说明 | 下面验收矩阵必做项全部有证据；“本地/浏览器测试”“原生验收”“真实外部同步”“发布”分别报告 |

连接实施可以分批交付，但不能把只接 Git 或只有连接表单当成多目标同步完成；不能因外部连接未配置而阻塞本地碎片能力。阶段 3 的清理依赖离线与恢复验证，不依赖阶段 4 的云账号授权或外部接入结果。若某目标暂时只完成备份，其设置和回执应明确写“备份”，不能冒充可双向编辑的同步。

## 7. 回滚与停止条件

### 7.1 必须停止继续迁移的情况

- 原始资料包与源文件的哈希/数量无法核对，或密匣密钥元数据缺失。
- 未知 schema、重复 ID 或读取失败被忽略，导致无法确定待保留数据范围。
- 新版误把旧资料索引为碎片、共享附件丢失、回收站跨范围删除，或私密内容未经明确操作进入公开索引、导出或远端。
- 多连接出现重复写入、反复回传、错误覆盖或删除传播不能隔离。
- 只有旧编辑器才能读取的格式失去可用恢复路径，或后续设计要求破坏现有磁盘格式兼容性却没有另行迁移方案。

停止仅针对相应迁移或连接动作；仍可安全使用的本地碎片能力继续工作，并显示具体失败对象和可恢复方式。

### 7.2 回滚路径

1. 暂停相关外部连接和迁移任务，保留操作结果、导入映射、队列与错误证据；先核对不确定写入的实际状态，避免重复发送。
2. 保存切换后新产生的碎片和附件副本。不能直接拿旧快照覆盖整个工作目录，否则会丢失迁移后新增内容。
3. 使用经过验证的旧版/恢复工具打开原始资料包或完整本地快照，先在独立目录验证可读性；原始目录默认仍在，无需反向重建被删除的数据。
4. 代码回滚只回退该阶段实际改动，不执行工作区全量 reset/clean，不覆盖用户原有修改。已有连接配置、Vault 路径、分支和远端不因回退而自动改变。
5. 新版导入生成的碎片不自动删除；按导入映射报告它们与原件的关系，是否清理副本由明确的后续操作决定。
6. 远端已经收到的数据不随本地程序回滚自动撤销；先对照目标记录和同步基线，再制定范围明确的恢复操作。不得自动 force push、删除远端记录或用旧备份覆盖新数据。

首轮迁移保持现有 Markdown、原始结构化文件和密匣密文的字节兼容。将来若改变磁盘 schema，应作为独立迁移设计重新验证旧版可读性，不能沿用本文件的回滚结论。

## 8. 本文档交付与后续实施边界

本文件交付的是可供实施和 review 的迁移设计。当前没有发生产品入口移除、数据导出、连接接入或旧数据转换；上述验收矩阵尚未执行。文档核对只检查范围、源码指向、内部链接和差异格式，不运行应用构建来冒充功能验证。

实施时优先完成数据可恢复性和公开/私密碎片的离线闭环，随后删除无关专属实现与依赖，再完成多连接和聊天链路。保留旧数据恢复能力是迁移要求，不是继续开发资料库、思维导图、多维表格或密匣独立工作台的授权；私密碎片本身仍是确定保留的日常能力。
