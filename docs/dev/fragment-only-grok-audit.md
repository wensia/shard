```markdown
**裁决：修订后实施。** 产品已收敛到碎片、私密是属性而非密匣工作台、本地离线独立成立、一主多备、飞书「不可变」是协议约束、迁移默认不删数据、文档/代码/离线/真同步分层，均与用户决策一致，不必重做。但主通道出站与备份收齐目前是两套互相打架的拓扑，会让常驻节点上的记录在 Git/夸克上静默缺失；再补几处私密外发与落盘边界后即可按方案实施。未要求的手机 App、协同编辑、专属工作台均不应加回来。

## P0

**1. 备份入队与「拉取不包装」矛盾，手机记录可能永远进不了 Git/夸克**

- 位置：`fragment-storage-sync.md` 0026–0028、0085–0087、0107、0148–0150、0162、0243–0244；`fragment-only-design.md` 0109、0136–0137、0187
- 场景：飞书为主通道、桌面为默认备份节点，手机经常驻节点写入；或只开夸克、无主通道。
- 后果：本地保存时「同时创建各目标待投递项」（0085），但从主通道拉取的操作不得再包装成本地操作（0107），因此不会为 Git/夸克入队。Git 备份又定义为聚合检查点（0148）。按 0085 会双写或在非备份节点假显示「待推送」；按 0107 则夸克/Git 没有手机那条。仅夸克时默认备份节点是桌面，桌面收不到节点数据，0187「节点能保存和备份」不成立。
- 现有条款不足：0026 的「收齐后再备份」与 0085 的「保存即全目标入队」并列；0137 只禁止他机接管分支，没定义备份入队时机。
- 最小修订：主通道 = 源节点按操作出站；备份 = 指定备份节点在应用/收齐后做检查点或快照，源节点不为备份目标建操作队列。非备份节点不得显示「Git 待推送」。无主通道时，备份节点必须是实际持有新内容的节点，否则回执只能写「节点已保存、未备份」。
- 验收：手机保存一条带附件碎片，桌面上线后 Git 与夸克含同一 ID 与附件；仅夸克且备份节点为关机桌面时，不得出现已备份到夸克的回执。

## P1

**2. AI 整理可把私密正文存成普通碎片并外发**

- 位置：`fragment-only-design.md` 0084、0094–0100；`fragment-storage-sync.md` 0069
- 场景：已解锁私密碎片上「整理」，保存走默认普通目的地。
- 后果：明文进入公开时间线、搜索、飞书/Git 和新 Agent 可读范围。转私密停出站管不到这条新建路径。
- 现有条款不足：只规定筛选不继承隐私、Agent 默认普通，未约束派生产物。
- 最小修订：派生产物默认继承来源隐私；来源为私密时禁止存成普通，除非走与「明文导出」相同的显式确认。
- 验收：私密来源整理后保存，公开搜索/新连接/Agent 读不到正文；要公开必须二次确认。

**3. 转私密后飞书已落盘修订仍是明文，却无与 Git 对等的清单**

- 位置：`fragment-only-design.md` 0100–0101；`fragment-storage-sync.md` 0073–0077、0129–0144
- 场景：普通碎片已写入飞书不可变修订后再转私密。
- 后果：公开投影可撤，Base 历史正文仍可读。Git 有暂停/另建目标，飞书没有「哪些副本仍明文」的说明，用户会以为已保护。
- 现有条款不足：0073 只说不承诺擦除旧历史，没有目标级预览。
- 最小修订：转私密预览按目标列出未发送 / 传输未知 / 已存在明文修订或快照。不自动删飞书记录；若要远端不再可读，只能暂停旧目标并新建不含该历史的目标。
- 验收：已同步飞书的条目转私密后，界面明确「飞书修订仍含旧明文」，不得显示全部副本已保护。

**4. 可移植内容与设备私有状态没有路径/托管对照**

- 位置：`fragment-storage-sync.md` 0059、0079；`fragment-only-migration.md` 0031–0033；`fragment-only-design.md` 0158
- 场景：阶段 A 把队列、已投递集合、运行锁放进现已被 Git 托管的 `.shard/`。
- 后果：待投递状态、token、「已完成」标记进 Git；或 `lockbox.json` 被「排除凭证」误删，密文无法恢复。
- 现有条款不足：只有原则，没有包含/排除清单。
- 最小修订：列可移植路径（含 `lockbox.json`、墓碑、修订）与设备私有路径（队列、远端映射、锁、凭证），并写明 Git/夸克各自包含什么。此表作为阶段 A 门禁。
- 验收：检查点不含凭证与他机投递标记；夸克恢复包含密文和 lockbox 元数据，不含明文口令。

**5. 去重键缺失或双 Agent 映射不一致时会重复建碎片**

- 位置：`fragment-storage-sync.md` 0105–0106、0178、0196、0237、0307；`fragment-only-design.md` 0164、0178
- 场景：Skill 未传去重键；或 Hermes 与 OpenClaw 同时处理同一条飞书消息却用各自事件 ID。
- 后果：重复碎片。0307 已把映射列为待验证，但工具未规定失败态，实现者可能补键放行。
- 现有条款不足：「模型不得自行重生成」没有「缺键即拒绝」；双 Agent 未钉死平台消息 ID。
- 最小修订：无稳定来源键则拒绝创建。双 Agent 必须用租户+chat+message+动作序号；该映射列入阶段 C 待验证门禁，未通过不得宣称幂等完成。
- 验收：缺键调用失败且无新文件；同一飞书 `message_id` 经两 Agent 只有一条碎片。

**6. 飞书「备份」可配，但没有协议**

- 位置：`fragment-only-design.md` 0129；`fragment-storage-sync.md` 0020–0026、0109
- 场景：Git 为主通道，同时打开飞书并标成备份。
- 后果：可能再写一套修订流（两个写入源），或只刷投影；再切回飞书主通道时游标/身份对不上。与「至多一个主通道」冲突。
- 现有条款不足：Git 有备份/主同步两套语义，飞书没有。
- 最小修订：首版飞书要么关、要么当唯一主通道。若必须同时留飞书副本，定义为备份节点在收齐后的只读快照/投影，不是第二套修订日志；升格为主通道必须走已有切换流程。夸克「双向」不要出现在可选项里（与 0212 对齐）。
- 验收：Git 为主时飞书不能选成第二个可写主通道；设置不出现未开放的夸克双向。
```
